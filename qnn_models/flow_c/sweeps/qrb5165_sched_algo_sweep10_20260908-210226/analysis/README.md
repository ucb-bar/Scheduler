# Solver Pareto panels, in the FPGA rerun's flow

Port of `RoSE/experiments/xpurt_rerun/analysis/` onto this sweep. Same figure,
same reading: **left** which solvers are Pareto optimal in quality against solve
time, **right** what the spread across workloads actually is, with the deadline
miss rate as a trailing column.

    python3 mk_qrb5165_csv.py
    PARETO_DATA=. PARETO_TAG=_predicted python3 plot_pareto_panels.py --wide
    PARETO_DATA=./measured PARETO_TAG=_measured \
      PARETO_NOTE="measured aperiodic makespan (median of 3 reps), 12 all-solver cells; hollow = predicted misses, not traced" \
      python3 plot_pareto_panels.py --wide

Figures land in `../plots/` (gitignored, like every other plot in this sweep).
The CSVs are regenerated by the first command from `../results/all_results.json`
and `../results/phase4_results.json`, both of which are committed, so nothing
here is a stored copy of data that already exists.

## Two panels, because this sweep executed its schedules

| | rows | `objective` is |
|---|---|---|
| `results.csv` | 504 = 42 cells x 12 solvers | the solver's PREDICTED value |
| `measured/results.csv` | 144 = 12 cells x 12 solvers | the MEASURED aperiodic makespan, median of 3 reps |

The reference only ever had the first. The substitution in the second is
`mk_fpga_csv.py`'s: minimise the makespan of one-shot work while periodic tasks
keep their periods. `wall_s` stays the solver's time in both — it is a property
of solving, not of running.

## Port diffs against the reference script

Three, each marked `PORT DIFF` in `plot_pareto_panels.py`:

1. **Non-discriminating exclusion.** The reference globs the RoSE spec tree for
   `discriminates: false`. Those specs describe the FireSim workloads, and this
   sweep's ported specs carry no such annotation, so `mk_qrb5165_csv.py`
   computes the same exclusion structurally — a family every one of whose cells
   is all-periodic has no makespan to minimise — and writes it beside the CSV.
   Here that is **`depth_chain`, `depth_nav`, `tight_loop`**: 12 of 42 cells,
   leaving 30. The reference's own comment records it getting this wrong once
   by hardcoding `tight_loop` and silently averaging `depth_chain` in.
2. **`PARETO_TAG` / `PARETO_NOTE`.** Separate output names and an appended
   provenance line, because there are two figures here and one of them carries a
   caveat that must travel with the image rather than live only in this file.
3. **`WALL_FLOOR`, and this one is load-bearing.** `wall_s` is recorded as
   `round(delta, 3)`, so any solve faster than 0.5 ms stores as exactly `0.000`
   — and the left panel's x axis is logarithmic, where zero is undefined and the
   marker silently disappears. On the reference's 126–801 op workloads nothing
   was ever that fast. These cells are **4–33 ops**, so `greedy`,
   `greedy_periodic`, `greedy_reserved` and `decomposed` all are, and four of
   twelve solvers vanished from the first render with no error. They are clamped
   to the 1 ms floor and the figure says so. The honest reading of that cluster
   is not "these solvers take 1 ms" but "this data cannot separate them".

## What the figures say

**Predicted** (30 cells): frontier `heft_edf → best-of-fast → pso`. The
CP-SAT arms all land on the same 18.30% mean as `pso` and `sa` for 10-300x the
solve time, so they are dominated. `heft` scores highest of all (19.64%) and is
drawn hollow — it misses 3.1% of periodic operations.

**Measured** (12 cells): frontier `greedy_reserved → best-of-fast → pso → sa →
cpsat:warmbest`. Gains are much larger against measured greedy (40-42% vs
16-18%), and `cpsat` falls off the frontier — the dominated-CP-SAT result the
reference reports, reproduced on hardware.

**Do not read the fine ordering off these panels.** ANALYSIS.md §1 puts 93% of
the pairwise orderings inside the leading group below this board's rep-to-rep
spread. What the panels resolve is the grouping and the tails.

## Known gap

`misses` in `measured/results.csv` is the PREDICTED count. The reference
recomputes it from the trace, and is right that "predicted misses would defeat
the purpose of plotting hardware" — this sweep did not record per-instance
release times, so the hollow markers on the measured panel are a property of the
schedule, not of the run. The figure's own caption says so. Closing this means
capturing per-entry start times in the phase-4 trace and deriving misses the way
`mk_fpga_csv.py` does.
